1. Ringkasan Sistem

AICMS mengelola permintaan perubahan (RFC) infrastruktur IT dari draf sampai ditutup: dokumen terkunci per revisi, tinjauan AI yang bersifat hanya saran, skor risiko deterministik, persetujuan berjenjang dengan pemisahan tugas (separation of duties), penjadwalan, pencatatan eksekusi manusia, tinjauan pasca-implementasi (PIR), dan jejak audit yang hanya bisa ditambah.

1.1 Arsitektur

KomponenFungsiPort host
webNext.js 14 App Router, TypeScript, Tailwind — antarmuka pengguna3000
apiFastAPI + SQLAlchemy async — aturan bisnis, REST /api/v18000
workerRQ worker — menjalankan tinjauan AI secara asinkron—
postgresPostgreSQL 16 — data perubahan, revisi, persetujuan, audit15432
redisRedis 7 — antrian pekerjaan16001

Penyimpanan dokumen memakai volume Docker docdata (adapter lokal). Adapter S3 tersedia di kode tetapi tidak diaktifkan pada stack bawaan.

1.2 Batasan yang wajib dipahami

  • AI hanya memberi saran. AI tidak menyetujui, menolak, mengubah status, atau menjalankan perintah.
  • Tidak ada push konfigurasi ke perangkat. Eksekusi dilakukan manusia; AICMS mencatatnya.
  • Pemeriksaan yang tidak didukung = “Tidak Dinilai”, tidak pernah “Lulus”.
  • Setiap temuan AI menyitir bukti (dokumen + baris/bagian, atau kolom RFC).
  • Isi unggahan tidak tepercaya. Percobaan prompt injection dilaporkan sebagai temuan SECURITY, bukan diikuti.
  • Rahasia disamarkan ([REDACTED]) sebelum konten dikirim ke AI atau disimpan sebagai bukti.
  • Revisi bersifat tetap. Mengubah RFC yang sudah diajukan membuat revisi baru; tinjauan dan persetujuan revisi lama menjadi kedaluwarsa.
  • Batas waktu tidak pernah menyetujui otomatis.

2.2 Sumber daya

  • CPU 2 core, RAM 4 GB kosong, disk 10 GB (build image + volume).
  • Akses jaringan ke registry Docker dan, bila memakai AI nyata, ke endpoint penyedia AI.

2.3 Port

Port hostDipakaiBila bentrok
3000WebUbah pemetaan di docker-compose.yml untuk service web
8000APIUbah pemetaan untuk service api
15432PostgreSQLBebas diubah; hanya dipakai untuk akses host (mis. psql)
16001RedisBebas diubah; hanya dipakai untuk akses host
Kenapa 15432 dan 16001? Windows dengan Hyper-V sering mencadangkan rentang port 5141–5940 sehingga 5432 dan 6379 gagal dipakai. Pemetaan port host sengaja digeser; port di dalam jaringan Docker tetap standar.

3. Instalasi

3.1 Unduh dan siapkan berkas

  1. Salin repositori AICMS ke direktori kerja, mis. D:\Aplikasi\AICMS.
  2. Buka PowerShell di direktori tersebut. Semua perintah berikut dijalankan dari root repositori.

3.2 Konfigurasi .env

docker compose membaca berkas .env di root. Mulai dari contoh yang disediakan:

Copy-Item .env.example .env

Nilai minimum yang harus diperiksa:

VariabelNilai devKeterangan
JWT_SECRETdev-secret-change-in-productionWajib diganti di luar pengembangan
ALLOW_LOCAL_LOGINtrueLogin lokal (username/password). OIDC belum diaktifkan
REVIEW_MODEqueuequeue = tinjauan AI lewat worker; inline hanya untuk uji
AI_PROVIDERmockmock = heuristik deterministik tanpa jaringan
STORAGE_BACKENDlocalDokumen disimpan di volume docdata
Jangan simpan rahasia nyata di .env.example. Berkas .env berisi kredensial dan tidak boleh dimasukkan ke repositori atau dikirim lewat surel.

3.3 Build dan jalankan

docker compose up -d --build

Pada start pertama, kontainer api otomatis menjalankan:

  1. alembic upgrade head — membuat seluruh tabel.
  2. python seed.py — mengisi pengguna contoh (idempoten).
  3. uvicorn app.main:app --port 8000 — menjalankan API.

Kontainer worker menyala setelah api dan Redis sehat.

Build pertama memakan 3–10 menit. Build ulang hanya perlu setelah kode berubah.

3.4 Pemeriksaan pasca-instalasi

  1. Status kontainer: 
    docker compose ps
    Kelima service harus running; postgres dan redis berstatus healthy.
  2. API hidup: 
    curl.exe http://localhost:8000/api/v1/ai/status
    Membalas JSON berisi provider dan label, mis. {"provider":"mock","label":"AI: DEMO/MOCK"}.
  3. Web hidup: buka http://localhost:3000 — halaman login muncul dengan bahasa Indonesia.
  4. Login uji dengan akun admin (lihat 6.2). Bila gagal, lihat Bab 5.3.

4. Konfigurasi Lanjutan

4.1 Penyedia AI

AI_PROVIDER menentukan mesin tinjauan:

NilaiPerilaku
mockHeuristik deterministik, tanpa jaringan. Setiap tinjauan diberi label DEMO/MOCK.
openaiEndpoint apa pun yang kompatibel /chat/completions: OpenAI, gateway proxy, Ollama (http://host:11434/v1), vLLM, LM Studio.

Pengaturan untuk openai:

VariabelContohKeterangan
AI_BASE_URLhttps://api.openai.com/v1Alamat penyedia, termasuk /v1
AI_API_KEYsk-...Kunci API
AI_MODELgpt-4o-miniNama model persis seperti di penyedia
AI_TEMPERATURE0.0Biarkan 0 agar hasil stabil
AI_MAX_TOKENS2000Batas panjang jawaban
AI_TIMEOUT_SECONDS60Batas waktu permintaan; lewat batas = tinjauan gagal
AI_MAX_DOCUMENTS10Jumlah dokumen per tinjauan
AI_MAX_DOCUMENT_CHARS12000Potongan teks per dokumen

Contoh blok .env:

AI_PROVIDER=openai
AI_BASE_URL=https://api.openai.com/v1
AI_API_KEY=sk-isi-kunci-anda
AI_MODEL=gpt-4o-mini
Penyedia yang berjalan di komputer host. Dari dalam kontainer, localhost menunjuk ke kontainer itu sendiri. Gunakan http://host.docker.internal:PORT/v1 (pemetaan host-gateway sudah ada di docker-compose.yml untuk api dan worker).
Kunci hilang tidak boleh jatuh ke mode mock secara diam-diam. Bila AI_PROVIDER=openai tetapi kunci/endpoint tidak valid, tinjauan gagal dengan pesan “Konfigurasi kredensial AI ditolak” atau “Layanan AI sedang tidak tersedia…”. Perbaiki konfigurasi lalu jalankan ulang tinjauan dari halaman perubahan.

Variabel OPENAI_API_KEY dan OPENAI_MODEL masih dibaca sebagai cadangan bila AI_API_KEY/AI_MODEL kosong.

4.2 Mode tinjauan

REVIEW_MODEPerilakuDipakai untuk
queueTinjauan dikirim ke worker RQ; status Tinjauan AI diperbarui otomatis saat selesaiNormal, semua lingkungan produksi
inlineTinjauan dijalankan di dalam requestUji otomatis dan pengembangan cepat saja
Diagnosa cepat. Status Tinjauan AI yang menggantung lama berarti worker mati atau tidak sehat. Cek docker compose ps worker dan Bab 5.3.

4.3 Penyimpanan dokumen

Bawaan: STORAGE_BACKEND=local, path di kontainer /data/docs, dipetakan ke volume docdata. Volume ini harus di-backup bersama database. Adapter S3-compatible tersedia di kode, tetapi tidak ada service S3 pada stack bawaan.

4.4 Autentikasi

  • Pengembangan: login lokal JWT. Token berlaku JWT_EXPIRE_MINUTES (bawaan 60 menit).
  • Produksi: sambungkan OIDC (OIDC_ISSUER, OIDC_CLIENT_ID, OIDC_CLIENT_SECRET) lalu matikan ALLOW_LOCAL_LOGIN.
  • Menutup tab atau memuat ulang setelah kode web dibangun ulang menghapus sesi — login kembali.

4.5 Database dan migrasi

# Terapkan migrasi terbaru secara manual
docker compose exec -T api alembic upgrade head

# Lihat revisi aktif
docker compose exec -T api alembic current

# Akses SQL langsung
docker compose exec -T postgres psql -U aicms -d aicms

Setiap perubahan skema selalu disertai satu migrasi Alembic. Jangan mengubah tabel secara manual di lingkungan yang sudah berisi data.

5. Pengelolaan Layanan

5.1 Start, stop, restart

TujuanPerintah
Menyalakan seluruh stackdocker compose up -d
Membangun ulang lalu menyalakandocker compose up -d --build
Mematikan seluruh stack (data tetap)docker compose stop
Mematikan dan menghapus kontainer (data tetap)docker compose down
Menghapus kontainer dan volume datadocker compose down -v
Restart satu servicedocker compose restart api

docker compose down -v menghapus database dan dokumen secara permanen. Hanya lakukan pada lingkungan pengembangan yang boleh di-reset, dan setelah memastikan tidak ada data yang perlu dipertahankan.

5.2 Menerapkan perubahan

Jenis perubahanPerintah
Kode API (Python)docker compose restart api
Kode workerdocker compose restart worker
Nilai .env (termasuk AI_*)docker compose up -d --force-recreate api worker
Kode web / gaya Tailwinddocker compose build web lalu docker compose up -d web
Skema databasedocker compose exec -T api alembic upgrade head
Restart API memutus request yang sedang berjalan. Hindari saat ada tinjauan AI atau eksekusi berlangsung. Tinjauan yang terputus dapat dijalankan ulang dari halaman perubahan; eksekusi tidak dirugikan karena statusnya tersimpan di database.

5.3 Log dan diagnosa

docker compose logs -f web          # log Next.js

5.4 Backup dan restore

# Backup database
docker compose exec -T postgres pg_dump -U aicms -d aicms > backup_aicms.sql

# Backup dokumen (volume docdata)
docker run --rm -v aicms_docdata:/data -v "${PWD}:/out" alpine tar czf /out/docdata.tgz -C /data .

# Restore database (lingkungan kosong)
Get-Content backup_aicms.sql -Raw | docker compose exec -T postgres psql -U aicms -d aicms

Cadangkan database dan volume dokumen sebagai satu pasangan — database menyimpan hash dokumen yang harus cocok dengan berkasnya.

Ganti seluruh password contoh sebelum sistem dipakai di luar pengembangan. Akun ini hanya untuk data sintetis.

6.3 Membuat dan mengelola pengguna

  1. Masuk sebagai Admin, buka menu Pengguna (hanya terlihat untuk Admin).
  2. Isi Nama pengguna, Username, Email, lalu pilih Peran. Satu pengguna boleh memiliki lebih dari satu peran.
  3. Simpan. Pengguna baru langsung dapat login.
  4. Untuk mengubah peran: buka pengguna, ubah pilihan peran, simpan. Perubahan tercatat di jejak audit.
  5. Untuk menonaktifkan: gunakan Nonaktifkan. Ini soft delete — riwayat tetap utuh dan akun tidak bisa login lagi.

Username dan email tidak dapat diubah setelah dibuat. Tidak ada fitur reset password mandiri; Admin membuat ulang akun bila password hilang.

6.4 Aturan pemisahan tugas (SoD)

  • Pemohon tidak boleh menyetujui RFC miliknya sendiri.
  • Setiap langkah persetujuan hanya diambil oleh pemegang peran langkah tersebut.
  • Langkah berjalan berurutan; langkah berikutnya terkunci sampai langkah sebelumnya selesai.
  • Keputusan bersifat permanen dan tercatat di audit; menolak atau meminta revisi wajib disertai komentar.
  • Persetujuan menempel pada satu revisi. Revisi baru membatalkan persetujuan lama.

7.1 Tahap 1 — Login

  1. Buka http://localhost:3000. Halaman login tampil tanpa menu navigasi sisi.
  2. Isi Username dan Password, lalu tekan Masuk.
  3. Bila berhasil, sistem membuka Ringkasan dan menampilkan nama serta peran Anda di bagian bawah menu kiri.

Bila gagal: pesan kesalahan tampil di halaman login. Periksa huruf besar/kecil password dan pastikan akun tidak dinonaktifkan Admin.

7.2 Tahap 2 — Buat RFC (draf)

Masuk sebagai Pemohon. Menu Permohonan Perubahan → tombol Buat RFC. Formulir terbagi tiga kartu.

Kartu “Ringkasan perubahan”

KolomWajibCara mengisi
JudulYaSatu baris, menyebut objek dan tindakan. Contoh: Upgrade IOS core switch gedung A
KategoriYaJaringan / Server / Aplikasi / Basis Data / Keamanan / Infrastruktur / Lainnya
Tipe perubahanYaStandard (pola dikenal, risiko rendah), Normal (perlu persetujuan penuh), Emergency (jalur cepat)
LingkunganYaProduksi / Staging / Test / Development / Disaster Recovery. Untuk perubahan Produksi, isi rencana rollback dengan lengkap.

Kartu “Detail teknis”

KolomWajibCara mengisi
Justifikasi bisnisYaMengapa perubahan dibutuhkan; dampak bila tidak dilakukan. Dasar penilaian approver.
DampakTidakLayanan, pengguna, atau jendela operasi yang terdampak, termasuk potensi gangguan.
Rencana implementasiYaLangkah berurutan bernomor. Tulis perintah yang akan dijalankan, tanpa password/community/API key.
Rencana ujiTidakPemeriksaan pasca-eksekusi yang menyatakan perubahan berhasil (ping, monitoring, login uji).
Rencana rollbackYaWajib. Cara kembali ke kondisi awal bila gagal, termasuk perkiraan durasi rollback.

Kartu “Cakupan”

KolomCara mengisi
Perangkat terdampakPisahkan dengan koma. Contoh: core-sw-01, fw-edge-02. Dipakai kalender untuk deteksi bentrok — isi bila diketahui.
Layanan terdampakPisahkan dengan koma. Contoh: VPN kantor pusat, e-mail

Tekan Simpan sebagai Draft. Sistem membuka halaman detail RFC dengan nomor perubahan (mis. CHG-2026-000063) dan status Draf.

Jangan menulis kredensial di kolom mana pun. Nilai seperti password/community tetap disamarkan sebelum dikirim ke AI, tetapi kolom RFC tidak melalui lapisan penyamaran yang sama dengan dokumen. Simpan rahasia di dokumen konfigurasi berlabel agar tersamarkan.

7.3 Tahap 3 — Unggah dokumen

Masih di halaman detail RFC, kartu Dokumen. Unggahan hanya diterima selama status mengizinkan revisi baru (Draf, Diajukan, Validasi Dokumen, Tinjauan AI, Perlu Revisi).

  1. Pilih Jenis dokumen. Bawaan CRF (Formulir Permohonan). Pilihan lain: MOP, Konfigurasi sebelum, Konfigurasi yang diajukan, Rencana rollback, Rencana uji, Rencana komunikasi, Analisis dampak, Lainnya.
  2. Pilih berkas: .pdf, .docx, .xlsx, .txt, .cfg, .yaml, .yml, .json. Maksimum 50 MB.
  3. Tekan Unggah. Pesan sukses menyebut nama berkas dan versi, mis. MOP-core-a.pdf v1 terunggah.
  4. Ulangi untuk setiap jenis. Minimum yang disarankan: CRF, MOP, Konfigurasi sebelum, Konfigurasi yang diajukan.
Format yang bisa dibaca AI (buka bagian “Format dokumen yang bisa dibaca AI” di kartu Dokumen): PDF berbasis teks, DOCX, XLSX, TXT, CFG, YAML, JSON. PNG/JPG dan PDF hasil pindaian tidak terbaca — belum ada OCR — dan AI menandainya “Tidak Dinilai”. Simpan dokumen sebagai PDF hasil ekspor, bukan foto.

Kolom Ekstraksi per dokumen menunjukkan Terbaca AI, Diproses, atau Gagal dibaca. Perbaiki dokumen “Gagal dibaca” sebelum mengajukan. Tombol Lihat / unduh membuka berkas asli untuk memeriksa isinya.

Unggahan ulang berkas dengan jenis yang sama menaikkan versi; versi lama tetap tersimpan.

7.4 Tahap 4 — Ajukan dan tinjauan AI

  1. Pastikan dokumen wajib sudah terunggah dan form RFC lengkap.
  2. Kartu Aksi → tekan Ajukan untuk review. Revisi dikunci permanen.
  3. Status bergerak ke Validasi Dokumen lalu Tinjauan AI. Halaman memantau dan memperbarui hasil secara otomatis setiap beberapa detik.
  4. Tunggu hingga muncul panel Tinjauan AI dengan rekomendasi, skor risiko, dan daftar temuan.

Yang dibaca dari panel tinjauan:

BagianArti
Label penyediaDEMO/MOCK berarti heuristik tanpa model nyata. Tanpa label ini, tinjauan dijalankan model sungguhan.
RekomendasiSetuju / Setuju dengan syarat / Minta revisi / Tolak — hanya saran untuk approver.
Skor risiko0–100. Dipetakan ke Rendah, Sedang, Tinggi, Kritis dan menentukan rute persetujuan.
TemuanSetiap temuan menyebut status (Lulus / Gagal / Tidak Dinilai / Info) dan bukti: nama dokumen + baris/bagian, atau kolom RFC yang disitir.
BatasanApa yang tidak dapat diperiksa AI (mis. topologi, baseline resmi) dan ditandai “Tidak Dinilai”.
  • Keputusan reviewer (panel tinjauan, peran Peninjau Teknis dan Admin) — berlaku untuk semua tingkat risiko, lihat 7.5.
  • Tinjauan Gagal: pesan bahasa Indonesia menjelaskan sebabnya (“Layanan AI sedang tidak tersedia…”, “Konfigurasi kredensial AI ditolak”, “Respons AI tidak dapat dibaca sistem”). Tekan Jalankan ulang tinjauan setelah penyebabnya diperbaiki. Sistem tidak mencoba ulang otomatis agar gangguan tetap terlihat.
  • Perlu Revisi: temuan berisiko menunggu keputusan reviewer, atau reviewer mengembalikan RFC. Reviewer dapat menerima (RFC lanjut ke persetujuan) atau mengembalikan ke pemohon. Pemohon menekan Buka ulang ke Draf, memperbaiki RFC/dokumen, lalu mengajukan lagi. Ini membuat revisi baru.
  • Menunggu Persetujuan: alur persetujuan dibuat otomatis sesuai tipe perubahan dan tingkat risiko.

Rute persetujuan bawaan:

RisikoUrutan persetujuan
RendahPeninjau Teknis → Manajer
SedangPeninjau Teknis → Manajer → Manajer Perubahan
Tinggi / KritisPeninjau Teknis → Manajer → Manajer Perubahan → Anggota CAB → Penyetuju Akhir
Tipe EmergencyManajer Perubahan → Manajer (jalur cepat)

Risiko yang belum dinilai tidak pernah dirutekan sebagai Rendah; bawaannya Sedang.

7.5 Tahap 5 — Keputusan reviewer atas hasil tinjauan AI

Temuan AI tidak pernah menyetujui atau menolak RFC. Bila ada temuan Gagal berisiko tinggi/kritis, RFC berhenti di Perlu Revisi sebagai status “menunggu keputusan reviewer” — bukan penolakan. Untuk semua tingkat risiko, peran Peninjau Teknis (atau Admin) memeriksa temuan secara manual lalu memutuskan. Panel Keputusan reviewer muncul di bawah daftar temuan selama status RFC Tinjauan AI atau Perlu Revisi.

TombolAkibat
Terima hasil tinjauanRFC diteruskan ke Menunggu Persetujuan, termasuk bila temuan tinggi/kritis masih terbuka — Anda yang menanggung keputusan itu. Rute persetujuan dibuat sesuai tipe dan risiko.
Kembalikan ke pemohonRFC ke Perlu Revisi untuk diperbaiki pemohon; catatan tampil sebagai alasan perbaikan. Persetujuan yang belum diputuskan dibatalkan.
  1. Buka RFC → baca setiap temuan beserta bukti dan batasannya.
  2. Tulis Alasan / catatan keputusan — wajib untuk kedua pilihan (mis. “Risiko diterima: rollback sudah diuji, eksekusi di luar jam sibuk”).
  3. Tekan Terima hasil tinjauan atau Kembalikan ke pemohon, lalu konfirmasi (Ya, terima / Ya, kembalikan).
  4. Keputusan tersimpan permanen: pelaku, waktu, dan alasan tampil di panel; tercatat di jejak audit (review.decision), termasuk daftar temuan tinggi/kritis yang di-override.
Batas kewenangan. AI tidak pernah menyetujui atau menolak. Reviewer menentukan langkah berikutnya; persetujuan akhir tetap lewat alur approval dengan pemisahan tugas, sehingga penerimaan reviewer bukan persetujuan perubahan. Temuan AI tidak dapat diubah — yang dicatat adalah keputusan manusia di sampingnya, dan Approver melihat RFC di jejak audit.

Pemohon melihat tujuannya: status Perlu Revisi dengan catatan reviewer, lalu menekan Buka ulang ke Draf untuk memperbaiki dan mengajukan ulang revisi baru.

7.6 Tahap 6 - Persetujuan berjenjang

Keluar dari akun pemohon, masuk sebagai pemegang peran langkah pertama.

  1. Buka menu Persetujuan. Inbox menampilkan tugas milik Anda, jumlah yang dapat diputuskan, dan yang menunggu langkah lain.
  2. Buka tugas. Halaman menampilkan Alur persetujuan di kiri dan Detail RFC di kanan.
  3. Baca bukti: justifikasi, dampak, rencana implementasi, rencana uji, rencana rollback, perangkat/layanan. Absennya rencana rollback ditampilkan mencolok dengan warna bahaya.
  4. Isi Komentar. Wajib untuk Tolak dan Minta Revisi; opsional untuk Setujui.
  5. Pilih Setujui / Minta Revisi / Tolak, lalu konfirmasi pada panel yang muncul.
  6. Lanjutkan dengan akun peran berikutnya sampai seluruh langkah selesai.
KeputusanAkibat
SetujuiLangkah ditandai selesai; langkah berikutnya terbuka. Bila langkah terakhir, status menjadi Disetujui.
Minta RevisiRFC kembali ke Pemohon sebagai Perlu Revisi; seluruh persetujuan dibatalkan.
TolakRFC menjadi Ditolak, final.
  • Tugas yang menunggu langkah sebelumnya menampilkan “Menunggu langkah persetujuan sebelumnya selesai”; tombol keputusan tidak aktif.
  • Tugas bertanda kedaluwarsa (revisi sudah diganti) tidak boleh diputuskan; minta pemohon mengirim ulang.
  • Approver tidak dapat menyetujui RFC miliknya sendiri.

7.7 Tahap 7 — Penjadwalan

Setelah status Disetujui, kartu Implementasi & tinjauan pasca-implementasi menampilkan formulir jadwal.

  1. Isi Mulai (WIB) dan Selesai (WIB). Keduanya dalam waktu Indonesia Barat (UTC+7).
  2. Tekan Jadwalkan. Status menjadi Terjadwal dan jendela muncul di Kalender.

Periksa bentrok lebih dulu: buka menu Kalender, atur rentang tanggal, dan baca hasil deteksi konflik.

Verdict kalenderArtiTindakan
▲ Jadwal bentrok terdeteksiAda perubahan lain yang berbagi perangkat/layanan pada jendela yang samaGeser jadwal atau koordinasikan sebelum eksekusi
◑ Konflik tidak dapat dipastikanSebagian perubahan tidak mencantumkan perangkat/layananLengkapi cakupan atau verifikasi manual; jangan anggap aman
● Tidak ada bentrok pada data yang tersediaSemua perubahan dalam rentang mencantumkan dependensiLanjutkan

7.8 Tahap 8 — Eksekusi dan catat hasil

  1. Buka halaman detail RFC. Panel Siap dieksekusi harus hijau dengan keterangan “Semua prasyarat terpenuhi”. Bila belum, daftar penyebab ditampilkan (mis. revisi disetujui bukan revisi terkini).
  2. Laksanakan perubahan secara manual sesuai MOP. AICMS tidak menjalankan perintah apa pun.
  3. Tekan Mulai implementasi. Status menjadi Sedang Dieksekusi dan waktu mulai aktual tercatat.
  4. Setelah selesai, isi formulir hasil:
    • Hasil — Sukses / Sukses dengan deviasi / Gagal / Rollback.
    • Catatan eksekusi — apa yang benar-benar terjadi, termasuk penyimpangan dari rencana.
    • Post-check lulus — centang bila pemeriksaan dari rencana uji lolos.
    • Bukti validasi layanan — mis. “monitoring hijau, ping 0% loss”.
  5. Tekan Catat hasil. Status menjadi Validasi Pasca-Eksekusi.

Bila hasil adalah Gagal atau Rollback, jangan menutup RFC pada tahap berikutnya sebelum PIR dan tindak lanjut dicatat.

7.9 Tahap 9 — PIR dan penutupan

  1. Isi Catatan PIR (wajib): hasil validasi layanan setelah perubahan, gejala tersisa, dan rekomendasi.
  2. Centang Post-check lulus hanya bila benar. Bila gagal, sistem menampilkan “Post-check gagal: tandai rollback, bukan selesai” dan tombol simpan tetap nonaktif.
  3. Tekan Simpan PIR & selesaikan. Status menjadi Selesai.
  4. Tekan Tutup perubahan. Status menjadi Ditutup dan RFC keluar dari daftar aktif.

7.10 Tahap 10 — Audit dan pemantauan

  • Ringkasan menampilkan perubahan aktif, menunggu persetujuan, tinjauan AI tertunda/bertanda, jadwal mendatang, dan hasil eksekusi.
  • Audit mencatat setiap aksi sensitif: pembuatan RFC, unggahan dokumen, tinjauan AI, keputusan persetujuan, transisi status, perubahan pengguna, dan penghapusan RFC. Kolom waktu dalam WIB, 50 baris per halaman, dapat disaring berdasarkan aksi.
  • Riwayat status di halaman detail RFC menampilkan kronologi transisi beserta pelaku dan alasan. Pelaku ditampilkan sebagai nama pengguna (mis. requester1, manager1), sehingga jelas siapa yang mengajukan, meninjau, menyetujui, dan mengeksekusi; transisi otomatis sistem ditandai otomatis.
  • Kalender memperlihatkan jendela implementasi yang disetujui/terjadwal/dieksekusi/divalidasi.

8. Kalender Perubahan

  • Menu Kalender menampilkan perubahan berstatus Disetujui, Terjadwal, Sedang Dieksekusi, dan Validasi Pasca-Eksekusi.
  • Filter: rentang tanggal (Dari/Sampai, hari kalender WIB), status, kategori, lingkungan.
  • Panel verdict di atas daftar menjelaskan apakah konflik dapat dipastikan. Sistem tidak pernah menyatakan aman bila data dependensi belum lengkap — hasilnya “Konflik tidak dapat dipastikan”.
  • Klik kartu perubahan untuk membuka detail RFC.

Semua waktu pada antarmuka ditampilkan dalam WIB (UTC+7). Nilai tanggal/jam yang Anda isi juga diperlakukan sebagai WIB.

9. Penghapusan Data Perubahan

Menu Permohonan Perubahan menyediakan penghapusan untuk peran Admin dan Manajer.

CaraPerilaku
Tombol Hapus per barisMenghapus satu RFC yang statusnya mengizinkan
Centang beberapa baris → Hapus terpilihBulk delete; hasil laporan menyebut yang berhasil dan yang ditolak beserta alasannya
Hapus semuaMenghapus seluruh RFC yang dapat dihapus pada halaman yang sedang ditampilkan
  • Soft delete: data tidak dimusnahkan. RFC hilang dari daftar untuk semua orang, tetapi tetap terlihat oleh Admin/Auditor dengan opsi termasuk-dihapus, dan seluruh jejak auditnya tetap utuh.

  • Hapus permanen (purge) hanya tersedia bagi Admin melalui API dan tidak diekspos di antarmuka.
  • Nomor perubahan RFC yang di-soft-delete tetap terpakai sampai di-purge.

11. Lampiran

11.1 Daftar periksa pemohon sebelum mengajukan

  • Judul menyebut objek dan tindakan.
  • Kategori, tipe, dan lingkungan sudah benar.
  • Justifikasi bisnis menjelaskan alasan dan risiko bila tidak dilakukan.
  • Rencana implementasi berisi langkah bernomor, tanpa kredensial.
  • Rencana rollback lengkap dengan perkiraan durasi.
  • Rencana uji menyebut kriteria keberhasilan yang dapat diperiksa.
  • Perangkat dan layanan terdampak diisi.
  • Dokumen CRF, MOP, konfigurasi sebelum, dan konfigurasi yang diajukan terunggah.
  • Tidak ada dokumen berstatus Gagal dibaca.

11.2 Daftar periksa approver

  • Rencana rollback ada dan realistis.
  • Tinjauan AI dibaca, termasuk temuan “Tidak Dinilai” dan alasannya.
  • Skor risiko cocok dengan rute persetujuan yang berjalan.
  • Tidak ada bentrok di kalender, atau bentrok sudah dikoordinasikan.
  • Komentar menyebut dasar keputusan.

11.3 Daftar periksa pelaksana

  • Panel Siap dieksekusi hijau.
  • Jadwal sesuai jendela yang disetujui.
  • Hasil dan bukti validasi dicatat apa adanya.
  • PIR disimpan; post-check tidak dicentang bila gagal.
